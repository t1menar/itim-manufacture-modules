# Требования к платформе Manufacture (core v2) для видео-пайплайна

Редакция 2, 2026-11-10. Сверено с `manufacture-core` (коммит `c4129f4`, контракт 0.1.0, envelope v2,
ADR 0001–0012, `docs/architecture.md`, `docs/messaging.md`). `manufacture-sdk-python` и
`manufacture-examples` пока содержат только README, поэтому SDK в сверке не участвует.

Цель: пайплайн из `docs/PIPELINE.md` (idea → scenario [research, script] → review → video-generation → review →
instagram-publisher) работает на ядре v2 сразу как рабочее решение. Документ перечисляет **только то, чего в
v2 нет или что он делает иначе**, и что ядру нужно для этого сделать. Нормативные слова: **MUST** —
обязательно до первого боевого запуска, **SHOULD** — желательно.

Принцип: ядро остаётся универсальным (ADR-0001). Всё доменное (сессии агентов, журнал публикаций, цены,
статусы идей, кеш знаний) живёт в модулях.

## 1. Решения по расхождениям

| Тема | v2 | Решение |
|---|---|---|
| Транспорт результатов | Брокер (ADR-0005), без HTTP-колбэков | **Принято.** Требуется поведение, а не транспорт: идемпотентность по `message_id`, `attempt.id` в каждом результате, отбрасывание результатов неактуальной попытки. |
| Fence | Уникальный `attempt.id` + lease (ADR-0006) | **Принято** при условии R5 (проверка перед необратимым действием). Монотонность не нужна: ядро хранит «текущую попытку» шага. Но в `architecture.md` остались упоминания `fence` (§3.1, §3.4, §5.2, §6.2, §6.5, §10.3, C4) — их надо привести к `attempt.id`, иначе в схеме БД появится лишняя колонка. |
| Контекст | `data` + JSON Merge Patch, `steps.<id>.output`, снапшоты по стадиям, claim-check `$blob` (ADR-0007) | **Принимаю модель v2 и снимаю своё прежнее предложение «манифест артефактов вместо merge-patch».** Патчи применяются движком один раз в транзакции с дедупликацией по `message_id`, поэтому риска дублей и порядка нет. Добавляются требования R4 и R9 (история визитов и правила для вложений). |
| Session state агента | Нет | **В платформу не добавляем.** Модуль хранит сессию в собственной БД по ключу `(run_id, stage)`; ядро обязано гарантировать стабильные `run_id`, `step_key` и номер визита (R3, R4). |
| Intent публикации и журнал | Нет, публикация — обычный шаг | **Не добавляем в ядро.** Журнал и защита от дублей остаются в `module-instagram-publisher` (D23, B6). Ядру нужен класс ошибки `attention` (он есть) и R3. |
| Гейт | Нет специального типа; человек = долгий шаг (`timeout: 7d`) | **Достаточно, если выполнить R1 и R2.** Отдельный тип стадии не нужен. |
| Бюджеты и стоимость | Нет | Нужно, R7. |
| Хуки завершения | Нет | Нужно, R6 (иначе `module-idea` не узнает, чем кончился запуск). |
| Цены моделей | — | Хранит и считает **модуль** (SDK даёт хелпер); ядро только суммирует. Прежнее требование «таблица цен в платформе» снято. |
| Формат пайплайна | YAML в БД ревизиями (ADR-0004) | Закрывает мой открытый вопрос. |
| Кеш знаний | — | Модуль `module-scenario`, не ядро. Закрывает открытый вопрос. |

## 2. Что v2 уже закрывает (повторно не делаем)

Реестр модулей через `module.online` со схемами; heartbeat и lease; outbox/inbox, quorum-очереди, DLX;
ревизии пайплайнов и модулей, запуск привязан к ревизии; неизменяемый запрос попытки; классы ошибок
`transient|fatal|attention`; `step.cancel`; `routes` с `max_visits` → `needs_attention`; `needs_attention` не
занимает слот; `run_queue` и `max_runs`; claim-check `$blob` (до 256 КиБ в конверте); пользователь брокера на
модуль; `dedup_key` запуска; audit, janitor/retention, метрики `mf_*`, SSE; `foreach` и `parallel`.

## 3. Недостающие требования

### R1. Ожидание человека без потери шага (MUST, до C4)
Проблема: шаг `review` ждёт ответа до суток и более. Если реплика модуля перезапустится, lease истечёт,
попытка станет `lost`, ядро создаст новую попытку и **бот пришлёт карточку второй раз**.
Требование: состояние шага `waiting` (сообщение `step.waiting {reason, expected_by?}`). В нём:
- lease приостановлен, heartbeat не обязателен;
- дедлайн задаётся отдельно и по умолчанию длинный;
- попытка остаётся текущей, и модуль завершает её обычным `step.succeeded` из любой реплики;
- run получает состояние/метку `waiting_human` в API, SSE и метриках (`mf_runs_waiting`).

### R2. Политика таймаута (MUST, до C4)
`retry` по таймауту человека бессмыслен. Нужно поле шага `on_timeout: fail | retry | attention`
(по умолчанию `retry` для обычных шагов). Для review — `attention`. Без этого просроченный гейт либо
дублирует карточку, либо роняет весь запуск.

### R3. Стабильный ключ шага и номер визита (MUST, до C4)
Внешние действия (публикация, отправка карточки) должны быть идемпотентны **между попытками**, а
`attempt.id` меняется при каждой попытке. В `step.requested` добавить:
- `step_key` = `uuid5(NS, "<run_id>:<stage>:<step_id>:<item_index>:<visit>")`, стабилен между попытками
  одного визита;
- `visit` (номер захода в стадию, 1 для первого; растёт при `goto`);
- `revision_of` и `comment` не нужны: они приходят через входную проекцию (R4).
SDK отдаёт их в `ctx`.

### R4. История визитов и вход ревизии (MUST, до C7)
Петля «отказ → доработка» возвращает run на раннюю стадию, и `steps.<id>.output` перезаписывается.
Требование:
- движок хранит выходы **каждого** визита; доступ из CEL: `steps.<id>.visits[n].output`,
  `steps.<id>.last`, `steps.<id>.visit` (номер);
- проекция `input` стадии-цели может ссылаться на предыдущий выход своей стадии и на выход ревью
  (`steps.review.output.comment`); для первого визита поля пусты;
- при отказе ядро не очищает контекст и снапшоты прежних визитов (нужны для аудита и отката);
- `max_visits` считается на цель перехода, а не на правило, и учитывается в `mf_*` метриках.
Пример: `routes: [{when: "steps.review.output.decision == 'rejected' && steps.review.output.target == 'scenario'", goto: scenario, max_visits: 3}]`.

### R5. Подтверждение попытки перед необратимым действием (MUST для публикатора, до C5)
Lease не защищает от «зомби»: модуль завис, lease истёк, пошла вторая попытка, а первая всё же пишет
`media_publish`. Результат такой попытки ядро отбросит, но пост уже вышел.
Требование: синхронный вызов `POST /api/v1/attempts/{attempt_id}/confirm` (токен модуля) с атомарной
проверкой «попытка текущая, lease жив, run не отменён, до дедлайна достаточно времени» и коротким
продлением lease. Возвращает `ok | superseded | cancelled | deadline`. Это единственное исключение из
«модулю нужны только брокер и S3» и касается только модулей с необратимыми действиями. Вдобавок модуль
держит собственный журнал по `step_key` (R3).

### R6. Хуки завершения запуска (MUST, до C7)
`module-idea` должен получить `in_production`, `done`, `failed` и стоимость. Варианты (достаточно одного):
- **A (рекомендую):** событие `run.finished {run_id, pipeline, status, data?, usage}` и подписка модуля в
  спеке (`spec.subscribe: [run.started, run.finished]`), доставка в его очередь, как `step.requested`;
- **B:** стадия `finally: [...]` в Pipeline, выполняется при любом исходе, получает `run.status`.
Без этого статусы идей пришлось бы опрашивать через gateway.

### R7. Расход и бюджеты (MUST, начало до C4, enforcement до первого боевого запуска)
- `step.succeeded`, `step.failed` и `step.heartbeat` принимают необязательное `usage`:
  `{cost_usd, tokens: {model: {input, output, cache_read, cache_write}}}`; модуль считает сумму сам.
- Движок суммирует по попытке, шагу, запуску и пайплайну; хранит в таблице `usage` (не в метках метрик);
  отдаёт в API, SSE и `run.finished` (R6).
- Пайплайн: `budget: {run_usd, warn_usd, day_usd}`. Превышение `run_usd` → `step.cancel{reason: budget}`,
  run в `needs_attention`; `warn_usd` → событие и метка; `day_usd` → новые запуски ждут в `run_queue`.
- Перед стартом шага с оценкой `min_budget_usd` (в манифесте модуля) движок не диспетчеризует шаг, если
  остаток меньше. SHOULD.

### R8. Действия оператора (MUST, до C9)
`retry step`, `resume`, `skip`, `cancel` с обязательным комментарием в `audit_log`. Для `unknown` исхода
публикации `retry` не должен вызываться по умолчанию: UI и `mfctl` просят подтверждение и показывают, что
ответил `attention`. Просмотр и повторная доставка DLQ (`mf.dead-letters`) из API, а не только метрика.

### R9. Размер контекста и вложения (MUST, до C7)
- `data` хранит управляющие значения и ссылки; ролик, обложка, транскрипты — только `$blob`.
- Blob неизменяем: запись под `blob_prefix` попытки, `sha256` обязателен, перезапись запрещена.
- Результат, который должен пережить TTL (`final.mp4`), помечается `keep`.
- Проекция `input` не передаёт всё `data` целиком (иначе каждый шаг получает полный контекст):
  для пайплайна видео все стадии используют проекции.
- Лимит снапшота и размер `data` проверяются при `apply`/в рантайме с понятной ошибкой.

### R10. Приоритет и очередь запусков (SHOULD, до C4)
`run.requested` принимает `priority` (из `ideas.priority`), `run_queue` выдаёт слот по приоритету, затем
FIFO. Нужен глобальный `max_runs` на пайплайн (уже есть) и интервал между стартами (`min_interval`) на
источнике или в `concurrency`.

## 6. Дополнительные приёмочные сценарии (к itest из плана)

1. Перезапуск реплики `review` во время `waiting`: карточка не дублируется, шаг завершается из другой реплики.
2. Таймаут `waiting` с `on_timeout: attention`: run в `needs_attention`, ни одной повторной карточки.
3. Два захода в стадию `scenario` (`goto`): `steps.scenario.visits[1]` и `[2]` сохранены, второй заход получил
   комментарий и предыдущий выход, `max_visits` останавливает на третьем отказе.
4. Результат устаревшей попытки: отброшен; `confirm` вернул `superseded` и модуль не выполнил действие.
5. Одна публикация, две попытки с одним `step_key`: внешний пост создан ровно один раз.
6. Превышение `run_usd`: `step.cancel{budget}`, run в `needs_attention`, `usage` в API и `run.finished`.
7. `run.finished` (успех, `failed`, `cancelled`) доходит до подписчика ровно один раз, даже после рестарта ядра.
8. Рестарт ядра и брокера в любой точке: нет потерянных и дублированных шагов, `waiting` сохраняется.
9. Blob 100 МБ (`final.mp4`) не попадает в `data`, перезапись под тем же ключом отклонена, `keep` переживает GC.
